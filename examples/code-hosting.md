# 代码托管

输入：我想管理团队代码并协同开发

底层需求：让代码变更可追踪、可合并，并可交付给其他人。

> 编辑案例，路线为概括性综合。时间不代表首创；来源页面可能仅支持当前能力。

## 历史路线

### 本地版本记录 · 早期路线

解决：记录文件修改历史

仍缺少：团队共享和合并困难

代表：本地版本控制

### 集中式版本控制 · 1990s 普及

解决：共享统一仓库

仍缺少：中央服务成为工作依赖

代表：CVS / SVN

### 分布式版本控制 · 2005 · Git

解决：让每个副本保有历史和分支能力

仍缺少：学习与合并仍有门槛

代表：Git

### 自托管仓库 · 并行路线

解决：控制托管环境与数据

仍缺少：需要独立维护基础设施

代表：组织内 Git 服务

### 协作式代码托管 · 当代路线

解决：把评审与协作聚合到仓库

仍缺少：平台迁移和工作流绑定

代表：GitHub

### AI 软件协作 · 探索中

解决：辅助理解与修改代码

仍缺少：代码正确性和评审责任仍需保证

代表：AI 开发工作流

## 为什么会发生跃迁

- **本地版本记录 → 集中式版本控制**：共享仓库协调团队改动。新问题：中央服务成为工作依赖。

- **集中式版本控制 → 分布式版本控制**：Linux 开发对速度和分布式的需求促成 Git。新问题：学习与合并仍有门槛。

- **集中式版本控制 → 自托管仓库**：协议开放允许独立运行托管。新问题：需要独立维护基础设施。

- **分布式版本控制 → 协作式代码托管**：评审与自动化围绕版本历史聚合。新问题：平台迁移和工作流绑定。

- **自托管仓库 → 协作式代码托管**：评审与自动化围绕版本历史聚合。新问题：平台迁移和工作流绑定。

- **协作式代码托管 → AI 软件协作**：生成模型开始参与开发流程，验证不能省略。新问题：代码正确性和评审责任仍需保证。

## 失败 / 停止路线

### Google Code · 2015–2016 · 关闭托管服务

为开源项目提供公共托管。 让开发者集中分享项目并追踪工作。

结果：平台逐步转为只读并关闭。 官方说明大量项目迁移，剩余维护工作受到垃圾内容等问题影响。

启示：网络效应和维护结构值得研究；具体商业原因不能由公告之外自行推断。
