# 在线支付

输入：我想做一个在线支付系统

底层需求：让客户完成付款，并让商户可靠地确认订单与款项状态。

> 编辑案例，路线为概括性综合。时间不代表首创；来源页面可能仅支持当前能力。

## 历史路线

### 银行转账 · 概括性路线 · 非首发年代

解决：跨账户转移资金

仍缺少：交易与订单匹配需要额外流程

代表：银行账户

### 银行卡在线支付 · 概括性路线 · 非首发年代

解决：让持卡人在线完成购买

仍缺少：商户需要处理集成与支付流程

代表：银行卡网络

### 支付网关 · 概括性路线 · 非首发年代

解决：把商户应用连接到支付处理

仍缺少：多种渠道仍需协调

代表：支付处理平台

### 数字钱包 · 概括性路线 · 非首发年代

解决：复用已保存的支付身份

仍缺少：钱包与地区支持有所不同

代表：PayPal

### 托管结账 · 概括性路线 · 非首发年代

解决：减少商户自行构建结账界面的工作

仍缺少：定制能力受提供方约束

代表：托管 Checkout

### 支付基础设施 API · 概括性路线 · 非首发年代

解决：在产品内组合支付与相关流程

仍缺少：异步状态、退款与对账仍需正确设计

代表：Stripe Payments

## 为什么会发生跃迁

- **银行转账 → 银行卡在线支付**：在线交易产生远程支付需求。新问题：商户需要处理集成与支付流程。

- **银行卡在线支付 → 支付网关**：标准接口帮助抽象不同处理环节。新问题：多种渠道仍需协调。

- **银行卡在线支付 → 数字钱包**：重复支付希望减少输入步骤。新问题：钱包与地区支持有所不同。

- **支付网关 → 托管结账**：成熟托管界面降低接入成本。新问题：定制能力受提供方约束。

- **数字钱包 → 托管结账**：成熟托管界面降低接入成本。新问题：定制能力受提供方约束。

- **托管结账 → 支付基础设施 API**：API 把成熟支付能力嵌入应用。新问题：异步状态、退款与对账仍需正确设计。

尚未收录经过核验的关闭产品；不据此推断支付历史没有失败路线。

## 可复用资源

- [Stripe Payments](https://stripe.com/payments)：查看所在地区支持情况、商户审核要求与费用，先在沙箱环境完成集成。 条件：商户身份、业务类型和地区需由服务提供方审核；不是所有人均可开通。

- [PayPal Checkout](https://developer.paypal.com/studio/checkout/standard/integrate)：查看所在地区支持情况、商户审核要求与费用，先在沙箱环境完成集成。 条件：商户身份、业务类型和地区需由服务提供方审核；不是所有人均可开通。

## 当前边界

成熟：托管结账、支付 API 集成

发展中：多支付方式整合、嵌入式支付体验

- **异步支付状态的可理解性**（假设）：从集成流程推导的假设，需通过真实订单场景验证。 验证：在沙箱中模拟成功、失败、延迟和退款，观察商户能否正确判断订单状态。

- **跨提供方的对账工作流**（假设）：对不同系统组合成本的研究假设，不构成财务建议。 验证：访谈商户并比较现有服务，确认具体重复录入与核对步骤。
